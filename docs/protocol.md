# Manette Protocol Specification

**Version:** 1 (draft)
**Status:** Source of truth. The Android app and the Windows companion are both written against this file and against `protocol/test-vectors.json`. If code and spec disagree, fix one of them deliberately, never silently.

---

## 1. Goals and non-goals

**Goals**
- Carry gamepad state from one or more phones to a PC with minimum latency.
- Each phone is an independent controller (its own session, its own virtual pad).
- Reject packets from anyone who has not paired with the PC.
- Be trivial to implement identically in Kotlin and C#.

**Non-goals (v1)**
- Confidentiality. Gamepad state is not secret; packets are authenticated but not encrypted.
- Reliable delivery. State is resent continuously, so a lost packet is healed by the next one.
- Bluetooth. The wire format here is for UDP. A future Bluetooth transport reuses the *state model* (section 5) but not the framing.

---

## 2. Conventions

- Transport: **UDP**, IPv4 (IPv6 allowed, nothing in the format depends on it).
- Default port: **26760** (configurable on the PC; the phone learns it via discovery, QR, or manual entry).
- All multi-byte integers are **little-endian**.
- Types: `u8`, `u16`, `u32` are unsigned; `i16` is signed two's complement.
- `bytes[N]` is a fixed-length raw byte array.
- Strings are UTF-8, length-prefixed with a `u8`.
- One UDP datagram carries exactly one message. Maximum message size is 128 bytes; larger datagrams are dropped.

---

## 3. Common header (8 bytes)

Every message starts with this header.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 2 | `magic` | Bytes `0x4D 0x4E` (ASCII `MN`). Anything else is dropped silently. |
| 2 | 1 | `version` | Protocol version. This document defines `1`. |
| 3 | 1 | `type` | Message type, see table below. |
| 4 | 4 | `session_id` | `0` before a session exists (HELLO, REJECT). Otherwise assigned by the PC in WELCOME. |

### Message types

| Type | Name | Direction | Authenticated by |
|---|---|---|---|
| `0x01` | HELLO | phone to PC | `device_key` |
| `0x02` | WELCOME | PC to phone | `device_key` |
| `0x03` | REJECT | PC to phone | none (hint only) |
| `0x10` | INPUT | phone to PC | `session_key` |
| `0x12` | PING | phone to PC | `session_key` |
| `0x13` | PONG | PC to phone | `session_key` |
| `0x20` | RUMBLE | PC to phone | `session_key` |
| `0x21` | BYE | either | `session_key` |

Unknown `type` values are dropped (this is how additive extensions stay compatible).

## 4. Authentication model

### 4.1 Keys

| Key | Size | How it is made | Lifetime |
|---|---|---|---|
| `pairing_secret` | 16 bytes | Random, generated by the PC when the user opens "Pair a phone" | Short-lived, single use |
| `device_key` | 32 bytes | `HKDF-SHA256(ikm = pairing_secret, salt = "manette-v1-pair", info = device_id)` | Permanent, stored by both sides after pairing |
| `session_key` | 32 bytes | `HKDF-SHA256(ikm = device_key, salt = client_nonce \|\| server_nonce, info = "manette-v1-session")` | One session |

`device_id` is a 16-byte random value generated once by the phone app on first launch.

Neither `pairing_secret` nor any key is ever sent over the network. The phone gets `pairing_secret` out-of-band (QR code or typed code), and both sides compute `device_key` independently.

### 4.2 Tags

- **Handshake messages** (HELLO, WELCOME) carry a **16-byte** tag: the first 16 bytes of `HMAC-SHA256(device_key, all preceding bytes of the message)`.
- **Session messages** (INPUT, PING, PONG, RUMBLE, BYE) carry an **8-byte** tag: the first 8 bytes of `HMAC-SHA256(session_key, all preceding bytes of the message)`.
- The tag is always the **last** field of the message and covers every byte before it, header included.
- Tag comparison **must be constant-time**.
- A message with a bad tag is dropped silently (no REJECT, to avoid giving scanners an oracle).

### 4.3 Pairing secret formats

The same 16 bytes are presented to the user in two forms:

1. **QR code** (preferred): a URI
   `manette://pair?v=1&h=<host>[,<host>...]&p=<port>&s=<secret>&n=<pc name>[&i=<install id>]`
   where `s` is the secret in unpadded Base32 (26 characters). Multiple hosts may be listed (Wi-Fi, Ethernet, a USB-tether adapter); the phone uses the one on the same subnet as one of its own addresses. The optional `i` is the PC's 8-hex install id (also the `id` in its mDNS TXT record), which lets the phone find the same PC again if its IP address changes. Receivers ignore a missing or malformed `i`.
2. **Typed code** (fallback): the same Base32 secret shown as `XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX`, with the host entered manually. The code is long on purpose. A short PIN would be brute-forceable offline from a captured HELLO, so v1 does not use one.

### 4.4 Pairing window rules (PC side)

- A `pairing_secret` is valid for **5 minutes** or until one phone pairs with it, whichever comes first. Pairing a second phone means showing a new QR.
- After a successful pairing the PC stores `{ device_id, device_key, name }` as a trusted device and discards the secret.
- Outside a pairing window, HELLOs are accepted only from trusted `device_id`s.

## 5. Gamepad state model

The canonical state is an Xbox 360-style pad. Every future controller layout (NES, PS1, and so on) maps onto this same state, so the wire format does not change when layouts are added.

### 5.1 Buttons (`u16` bitmask)

The bit values deliberately match the Windows XInput `wButtons` layout, so the PC side can pass them straight through.

| Mask | Button |
|---|---|
| `0x0001` | D-pad Up |
| `0x0002` | D-pad Down |
| `0x0004` | D-pad Left |
| `0x0008` | D-pad Right |
| `0x0010` | Start |
| `0x0020` | Back |
| `0x0040` | Left stick click (L3) |
| `0x0080` | Right stick click (R3) |
| `0x0100` | Left bumper (LB) |
| `0x0200` | Right bumper (RB) |
| `0x0400` | Guide (Xbox button) |
| `0x0800` | Reserved, send as 0 |
| `0x1000` | A |
| `0x2000` | B |
| `0x4000` | X |
| `0x8000` | Y |

### 5.2 Axes

| Field | Type | Range | Notes |
|---|---|---|---|
| `lt`, `rt` | `u8` | 0 to 255 | 0 is released, 255 is fully pressed |
| `lx`, `ly`, `rx`, `ry` | `i16` | -32768 to 32767 | 0 is centered |

**Sign convention:** positive `x` is right, positive `y` is **up** (XInput convention). Android screen coordinates have `y` increasing downward, so the phone must invert Y when building the state. This is the classic bug to cover with a test. The rule is `wire_y = clamp(-screen_y, -32768, 32767)`; the clamp matters because negating -32768 does not fit in an `i16`.

Deadzones are **not** applied on the wire. Send raw values; the PC (or the game) applies deadzones.

## 6. Messages

### 6.1 HELLO (`0x01`), phone to PC

Sent to open a session. `session_id` in the header is `0`.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 8 | header | `type = 0x01` |
| 8 | 1 | `flags` | Bit 0: `PAIRING` (the proof was made with a key derived from a freshly scanned `pairing_secret`). Other bits reserved, send 0. |
| 9 | 16 | `device_id` | |
| 25 | 8 | `client_nonce` | Random, fresh per HELLO |
| 33 | 1 | `name_len` | 0 to 32 |
| 34 | N | `name` | Device name, UTF-8 |
| 34+N | 16 | `tag` | HMAC with `device_key` |

Maximum size: 34 + 32 + 16 = 82 bytes.

**PC handling**
1. If `PAIRING` is set and a pairing window is open: derive `device_key` from the open `pairing_secret` and the received `device_id`, verify the tag. On success, store the device as trusted and close the window.
   If `PAIRING` is set but the window is closed (it is single-use) and this `device_id` is **already trusted**, treat the HELLO as an ordinary trusted one: verify the tag against the stored `device_key`. This is what lets a phone retry after the first WELCOME was lost. A `device_id` that is not trusted gets REJECT reason 4.
2. Otherwise: look up `device_key` by `device_id` and verify the tag. Unknown device or bad tag: drop silently (or REJECT with reason 1, see 6.3).
3. Create a session (or reuse the existing one for this `device_id`, see section 8), allocate a virtual pad, and reply with WELCOME.

### 6.2 WELCOME (`0x02`), PC to phone

`session_id` in the header is the newly assigned (non-zero) id.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 8 | header | `type = 0x02`, `session_id` = assigned id |
| 8 | 1 | `flags` | Bit 0: `RESUMED` (an existing session and virtual pad were reused). Bit 1: `PAIRED_NOW` (this HELLO completed pairing). |
| 9 | 1 | `slot` | Virtual pad number the OS assigned, 0 to 3. `0xFF` if unknown or not assignable. Informational. |
| 10 | 2 | `rumble_hz_max` | Maximum RUMBLE messages per second the PC will send. 0 disables rumble. |
| 12 | 8 | `server_nonce` | Random |
| 20 | 16 | `tag` | HMAC with `device_key` over all preceding bytes **followed by** the HELLO's `client_nonce` |

Including `client_nonce` in the tag proves to the phone that the PC holds `device_key` and is answering *this* HELLO, not replaying an old WELCOME.

After WELCOME both sides derive `session_key` (section 4.1).

### 6.3 REJECT (`0x03`), PC to phone

Unauthenticated. The phone may show the reason to the user but **must not** change any trust or key state because of it.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 8 | header | `type = 0x03`, `session_id = 0` |
| 8 | 1 | `reason` | See below |
| 9 | 1 | `max_version` | Highest protocol version the PC supports |

| Reason | Meaning |
|---|---|
| 1 | Not paired or bad proof |
| 2 | Unsupported protocol version |
| 3 | Server full (no free virtual pad) |
| 4 | Pairing window is not open |
| 5 | Rate limited |

Because REJECT can be forged, it is a UI hint only. A phone that never receives a WELCOME simply retries and eventually reports "could not connect".

### 6.4 INPUT (`0x10`), phone to PC

The hot path. Fixed size: **30 bytes**.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 8 | header | `type = 0x10`, `session_id` = assigned id |
| 8 | 2 | `seq` | `u16`, wraps. Starts at 0 on each new session. |
| 10 | 2 | `buttons` | Bitmask, section 5.1 |
| 12 | 1 | `lt` | |
| 13 | 1 | `rt` | |
| 14 | 2 | `lx` | `i16` |
| 16 | 2 | `ly` | `i16` |
| 18 | 2 | `rx` | `i16` |
| 20 | 2 | `ry` | `i16` |
| 22 | 8 | `tag` | HMAC with `session_key` |

Each INPUT carries the **full** state, not a delta. That is what makes loss and reordering harmless.

**Sequence handling (PC side)**
- Treat `seq` as a serial number: a packet is *newer* if `(int16)(seq - last_seq) > 0`.
- Drop packets that are not newer. Apply newer ones and update `last_seq`.
- Verify the tag **before** touching `last_seq`.

### 6.5 PING (`0x12`) and PONG (`0x13`)

Used to measure round-trip time and to keep NAT or firewall state warm. Both are 20 bytes.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 8 | header | `type = 0x12` or `0x13` |
| 8 | 4 | `timestamp` | Phone's monotonic millisecond clock. The PC copies it into the PONG unchanged. |
| 12 | 8 | `tag` | HMAC with `session_key` |

The phone computes RTT as `now - timestamp`. Clocks are never compared across devices.

### 6.6 RUMBLE (`0x20`), PC to phone (optional)

Size: 20 bytes.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 8 | header | `type = 0x20` |
| 8 | 2 | `seq` | Separate counter from the phone's INPUT `seq`, same serial-number rule |
| 10 | 1 | `large` | Strong (low-frequency) motor, 0 to 255 |
| 11 | 1 | `small` | Weak (high-frequency) motor, 0 to 255 |
| 12 | 8 | `tag` | |

Phone vibrators are weak and single-motor, so the phone maps `max(large, small)` to an amplitude. Rumble is a v1.1 feature; implementations may ignore RUMBLE, and the PC only sends it if `rumble_hz_max > 0`.

### 6.7 BYE (`0x21`), either direction

Size: 16 bytes. Header plus an 8-byte tag. Ends the session immediately and, on the PC, resets the pad to neutral and starts the grace period (section 8).

## 7. Sending behavior (phone)

- Send an INPUT **immediately** whenever the state changes. Do not wait for a poll tick.
- While nothing changes, send the current state at **20 Hz** (every 50 ms) as a keepalive.
- After a change that **releases** something (a button up, a stick returning to center), send the packet **twice**, about 2 ms apart. A lost release is the one loss users notice (a stuck input), so it is worth one redundant datagram.
- Coalesce rapid multi-touch changes that occur within the same frame into one packet.
- Increment `seq` for every INPUT sent, including redundant ones.
- Use a socket on a dedicated high-priority thread; never send from the main thread.
- Send a PING about once per second for the latency readout.
- Every HELLO, including a retransmission after a 500 ms timeout, uses a **fresh `client_nonce`**, and the phone accepts only the WELCOME bound to its **newest** nonce. If the PC answered two HELLOs, the later one is the one it keeps, so this keeps both sides on the same session key and stops an old or replayed WELCOME from installing a stale key. Stay under the PC's rate limit (about 2 HELLOs per second is fine).
- If no PONG arrives for 3 seconds, treat the session as lost and send a fresh HELLO (new `client_nonce`). The PC only accepts INPUT while a session is ACTIVE or STALE, so after a long outage this is how the phone gets its pad back; a `RESUMED` WELCOME restores play on the same slot.

## 8. Session lifecycle (PC side)

```
            HELLO ok                        packets arriving
   (none) ----------> ACTIVE <-----------------------------+
                        |  ^                               |
        no packet 500ms |  | packet or HELLO resumes       |
                        v  |                               |
                      STALE ---- 10 s no packet ---> GRACE ---- 10 s more ---> DESTROYED
                  (pad reset to neutral)         (pad kept, neutral)       (virtual pad removed,
                                                                             slot freed)
```

| State | Condition | Behavior |
|---|---|---|
| ACTIVE | Valid packets arriving | Apply state to the virtual pad |
| STALE | No valid packet for 500 ms | Reset the pad to **neutral** (all released, sticks centered) so a vanished phone never leaves a button held |
| GRACE | BYE received, or STALE for 10 s | Keep the virtual pad alive so a reconnect keeps the same slot and the game does not lose its controller |
| DESTROYED | GRACE expired (10 s) | Remove the virtual pad, free the slot, discard `session_key` |

**Reconnect:** a valid HELLO from a `device_id` that has a session in STALE or GRACE returns WELCOME with `RESUMED` set and the same virtual pad. A fresh `session_id` and `session_key` are issued, since the nonces are new.

**Multiple phones:** each `device_id` owns at most one session. A second HELLO from the same `device_id` replaces the old session. Different `device_id`s get different sessions and therefore different virtual pads. XInput on Windows has 4 slots; when all are taken, the PC replies REJECT reason 3.

**Source address:** the PC records the source IP and port of each authenticated packet and sends replies there. If a valid INPUT arrives from a new address (phone moved between Wi-Fi and USB tether, for example), the PC updates the stored address, because the tag already proves the sender.

## 9. Discovery

**mDNS / DNS-SD (PC advertises, phone browses)**

- Service type: `_manette._udp.local.`
- Instance name: the PC's display name.
- Port: the UDP port.
- TXT records:

| Key | Value |
|---|---|
| `v` | Highest protocol version supported, for example `1` |
| `id` | 8 hex characters identifying this PC installation |
| `pair` | `1` if a pairing window is open, else `0` |

**Manual IP** is a first-class path, not a fallback afterthought: it covers networks that block multicast and the USB-tethering case (where the PC is usually the phone's gateway address). The phone remembers the last-used address per paired PC.

The responder answers a querier on UDP port 5353 by multicast. A querier on any other port cannot hear multicast, so it gets a **unicast** reply to its own address and port that echoes its query id (RFC 6762 section 6.7). Android's NSD uses port 5353; simple tools and the FakeClient `discover` command use the unicast path.

Discovery only helps the user *find* a PC. It conveys no trust; trust comes only from the pairing handshake.

## 10. Versioning and extension

- `version` is checked on every message. A PC that receives a version it does not support replies REJECT (reason 2, with `max_version`) to a HELLO and drops everything else.
- **Within a version, layouts are fixed.** Any change to an existing message's layout requires a new version.
- **Additive changes** (new message types, new bits in `flags`) do not bump the version, because unknown types are dropped and reserved bits are sent as 0 and ignored on receipt.
- A future Bluetooth HID transport shares section 5 (the state model) but defines its own framing and pairing; it does not use this document's message layouts.

## 11. Security summary

| Threat | Mitigation |
|---|---|
| Stranger on the LAN injects input | Every message carries an HMAC; no pairing means no key |
| Replay of a captured INPUT | `seq` must be newer; session keys are fresh per session via nonces |
| Replay of a captured HELLO | Harmless: the attacker cannot derive `session_key` without `device_key` |
| Brute-forcing the pairing secret | 128-bit secret, 5-minute single-use window |
| Spoofed WELCOME | WELCOME is authenticated and bound to the HELLO's `client_nonce` |
| Resource exhaustion by HELLO flood | Rate-limit HELLOs per source address; verify the tag before allocating anything |
| Eavesdropping on input | **Not mitigated by design** (non-goal) |
| Forged REJECT | Phone treats REJECT as a hint only |

**Known limits.** An attacker on the path who sees a packet *before it is delivered* could in principle replay it with a higher `seq` than the real stream; this is accepted for v1 given the low stakes (gamepad state on a local link). Full encryption can be added in a later version if needed.

## 12. Test vectors

`protocol/test-vectors.json` holds byte-exact cases that **both** codecs must reproduce. It is generated by `protocol/generate_test_vectors.py` (standard library only); regenerate it whenever this document changes a layout. Each vector provides inputs (keys, nonces, state values) and the expected hex output. Required coverage:

- INPUT encode and decode for: all released; every single button; full-range triggers; stick extremes (`-32768`, `32767`); Y-axis inversion from a screen-space input.
- HKDF outputs for `device_key` and `session_key` from fixed secrets and nonces.
- HELLO and WELCOME with valid tags, and the same messages with one flipped bit (must fail verification).
- `seq` wraparound: `65535` followed by `0` is *newer*; `0` followed by `65535` is *older*.

### Worked example (unauthenticated body)

An INPUT for session `42`, `seq = 1`, button **A** pressed, `rt = 255`, left stick halfway right (`lx = 16384`), everything else zero. The first 22 bytes, before the 8-byte tag:

```
4D 4E 01 10  2A 00 00 00  01 00  00 10  00 FF  00 40  00 00  00 80  00 00
magic  ver type  session    seq   btns   lt rt   lx     ly     rx     ry
```

Here `rx` is -32768 (`0x8000`), written little-endian as `00 80`. Field by field:

| Field | Value | Bytes |
|---|---|---|
| magic | `MN` | `4D 4E` |
| version | 1 | `01` |
| type | INPUT | `10` |
| session_id | 42 | `2A 00 00 00` |
| seq | 1 | `01 00` |
| buttons | A (`0x1000`) | `00 10` |
| lt, rt | 0, 255 | `00 FF` |
| lx | 16384 | `00 40` |
| ly | 0 | `00 00` |
| rx | -32768 | `00 80` |
| ry | 0 | `00 00` |

Total before tag: 22 bytes. With the tag: 30. Using the session key from `test-vectors.json`, the tag is `a8a88e3ce888ee12`, so the full packet is `4d4e01102a0000000100001000ff0040000000800000a8a88e3ce888ee12`. Tags are produced by `protocol/generate_test_vectors.py`; never hand-compute them.

## 13. Open questions to settle before coding

1. **Port number.** 26760 is a placeholder. Confirm it does not collide with anything you run, and make it configurable.
2. **Timing constants** (50 ms keepalive, 500 ms stale, 10 s grace). These are starting points; tune them after latency testing.
3. **Redundant release packet.** Keep it only if testing shows lost releases on real Wi-Fi. It costs almost nothing, but measure before treating it as settled.
4. **Guide button.** XInput does not officially expose it. The ViGEm X360 target does support it, so confirm that against the library version you pin.
5. **Rumble** is specified but can ship later.
